## Block J — Activity-aware pacing

- **T86** — `ActivityProfile.cs`: a weekly activity *shape* — 168 buckets (day-of-week × local hour) holding `p(active)`, the recency-weighted share of observed weeks in which that hour saw at least one request. Built from `~/.claude/projects` timestamps because `usage-history.jsonl` is pruned at 8 days and structurally cannot see other weeks; only timestamps are read, not even token counts. Weeks are the rolling windows `[now−7(w+1)d, now−7w d)`, so every week contains each bucket exactly once and no partial-week correction is needed. Two anti-overfitting guards: 0.8/week exponential decay (half-life ≈3 weeks) and a blend toward the user's own flat active-rate prior worth 1.5 weeks of evidence, so a single holiday week cannot claim nobody works on Wednesdays — on the dev machine's 6 weeks that puts a 7% floor under the sleeping hours rather than a zero, which is the honest reading given usage from another machine leaves no local transcript. Presence per bucket, not request counts: one frantic afternoon must not outvote five ordinary ones. Cached at `%LocalAppData%\ClaudeTray\activity-profile.json` (~1.5 KB, 168 rounded floats) and recomputed after 20h; a cold scan of 93,856 requests across 6 weeks takes ~15s, which is why it is a daily cache and not a per-open scan, and it uses substring tests rather than `JsonDocument.Parse` per line. `ExpectedActiveHours(from, to)` — Σ p over the hours a span covers, pro-rating both ends — is the accessor T87 will spend quota against. Headless `--activity` prints the week as a heatmap with per-day active hours, the busiest bucket, and the expected active hours ahead (`--numbers` for raw percentages, `--refresh` to force a rescan, `--root` for a fixture tree). Internal: no user-facing surface until T87 puts the shape on the chart.
- **T87** — The weekly projection now follows that shape instead of a uniform slope (`ActivityShape.cs`). Calibrated per *active* hour — `rate = util / active_hours_measured_in_this_window`, with the measured hours coming free from the transcript samples `UsageReport` already scans (`WindowPace.MeasuredActiveHours`) — then spent forward as `util + rate × Σ p` over the remaining wall-clock hours. It degrades correctly by construction: where the remainder's active/idle mix matches the elapsed one it reproduces the old straight line exactly, and it only diverges where the mix genuinely differs. On the dev machine's real profile the landing moved from a straight-line time to **Thu 13:45**, a working afternoon. Faint **amber** bands mark the projected-idle stretches (red stays reserved for `OutageBandBrush` = "no reading was logged"; past idle gets no band, the curve is already flat there), with a "usually idle" legend item that appears only when there are bands, and the bands clip at the landing point rather than decorating a stretch the projection has given up on. Deliberate scope: weekly window only, the grey even-pace line / verdict chip / tray icon stay wall-clock, and below 3 weeks of coverage (or under 2 measured active hours, or already at the limit) `Build` returns null and the straight line is drawn instead. Copy hedges — "around 13:45", never a to-the-minute claim — and the method note states the limitation that usage from another machine or claude.ai leaves no local transcript, so locally-detected idle isn't necessarily real idle. Ten new keys across all five `lang/*.json`. - **T98** — `LiveRate.cs`: the rolling rate that sits **beside** the window average, never instead of it. The window is **age-weighted**, and that is the whole design: a plain rectangular window was built first and measured wrong in exactly the way this metric must not be — one 60k-token turn pinned the display at 1,000 tok/s for a full minute after the work stopped, then dropped to zero in a single step. Two bugs the verification turned up, both fixed here: the reader took the **first** parseable settings file, so a near-empty `~/.claude/.claude.json` (anything that runs with `CLAUDE_CONFIG_DIR=~/.claude` creates one) shadowed the real `~/.claude.json` and the page fell back to a coarse "Claude Team" with no holder, org or dates — it now prefers whichever file actually names an account; and the check itself was *creating* that litter by overriding the config dir even for the default profile, which it no longer does. `--profiles [--check]` prints the auth reading, whether it counts against the subscription, and the CLI's confirmation beside it.

- **T123** — Switching profiles, and the list that makes it possible. `Settings.Profiles` is the tray's own record — `{Label, ConfigDir, WorkDir}` and **nothing else**: no address, no token, no plan, so the tray never becomes a second store of somebody's credentials and a `/login` that changes the account inside a dir needs no update here. The editor lives on the **Claude Code** page (that page is about launching Claude Code, which is exactly what a profile decides — and it already has the Save button, which the read-only System page deliberately hides): add / rename / remove-from-list, where **rename is just a text box** (no dialog) and typing into a discovered profile is what registers it, since a name only persists if the tray remembers it. **Remove never deletes the folder** — it holds transcripts, memory and settings — and if discovery can still see the dir it comes straight back as a discovered profile, which is the honest meaning of "remove from list". Then the tray's **Open Claude Code** becomes a submenu, one entry per profile, launching with that profile's `CLAUDE_CONFIG_DIR` **and** its own working directory (without which one click would open the work account inside a personal repo). Not a single write into a config dir: `ProcessStartInfo.Environment` carries the dir (which forces `UseShellExecute = false` — noted in a comment, since `Environment` is silently ignored otherwise), and Claude Code creates a missing dir itself. A profile with no credentials file is marked *"— entrar"* and its entry runs `claude auth login`, with `--email` prefilled **only** from an `oauthAccount` the config already names — the one case where the tray knows the address without ever having asked for it, and it is passed only when it is unambiguously an address, since it lands on a `cmd.exe` command line and comes off disk. The separate per-profile sign-in item the task sketched was folded into this: the only profile that needs one is a profile without a login, and a second submenu of the same names is menu bloat. The submenu is rebuilt in place when the list is saved, so it never waits for a restart. Verified against a synthetic second profile: `--profiles` now prints each entry's menu label, resolved command, `CLAUDE_CONFIG_DIR` and working directory — the same helpers the click path uses, so the decision is checkable without a tray. One efficiency fix the work exposed: the window was running two full discovery sweeps (the editor's and the System page's) — now one, invalidated when the list is edited.

- **T122** — A **profile** is a config dir, and the tray can now see all of them. `ClaudeAccount.Read` takes a directory (it read one global path before) and `Discover` returns every profile on the machine, default first, from six sources with no guessing: the dir this process would use, `~/.claude`, an `env.CLAUDE_CONFIG_DIR` in either one's `settings.json`, the same key in each registered project's `.claude/settings.json` / `settings.local.json` (files `ContextScanner` already opens, so the source is free), the `~/.claude-*` convention, and a caller-supplied registered list (which T123's editor will feed — `--profiles [dir...]` exercises it today). A candidate qualifies on `.credentials.json`, a `.claude.json` naming an account, or explicit registration — that last clause is what will cover a dir that exists but has never been logged into, and it is why an *un*registered empty dir is correctly skipped rather than listed as a profile with no plan. **The bug this task existed to avoid**: the old reader fell back to `~/.claude.json` whenever `<dir>/.claude.json` was missing, which for a second profile would have read the default account's identity into it — the fallback is now offered *only* for the home dir, verified against a synthetic second profile that came back with its own account uuid, its own plan and its own project count. Identity is the `accountUuid`, so one account reached through two paths (a copied config, a junction) is listed once, under the first path. Labels are derived, never typed: the organization name, else "Personal" for an account without one, else the folder name. The page grew a **picker** rather than one stacked card per profile — six rows times N profiles is a scroll wall, and repeating a card per profile means building layout in code-behind, which this repo deliberately doesn't do; the picker keeps the page one screen and switching it re-renders every row from that profile's own files. Hidden entirely when there is one profile, which is the normal case. UNC project paths are skipped and the probe is capped at 200, because a dead share can block a stat for seconds and this runs while the window is being built.

## Block N — System information

- **T120** — A **System information** page in Settings, answering "which plan is this login actually on?" from what Claude Code already keeps on disk. `ClaudeAccount.cs` reads `.claude.json` and `.claude/.credentials.json` into one nullable-everywhere reading: the plan named the way a person says it (`userRateLimitTier` → **Claude Max 5x**, with the raw tier, seat tier and billing type as its qualifier line, and an unmapped tier prettified verbatim rather than dropped — a plan we haven't seen yet should still read, and be recognizable in a bug report), the holder, the organization and role, extra usage, the account/first-token dates, and the stored sign-in's own expiry; then the install (CLI version from the native installer's version store, install method, auto-update, project count, the config folder with **Open**, `CLAUDE_CONFIG_DIR` honoured) and the machine (tray version and location, Windows build, .NET runtime, architecture, the app's data folder). Read-only by construction — it opens files, never writes one, touches no transcript (§I.1 untouched: this is configuration, not conversation), and reads the credentials file **only** for `expiresAt`, `subscriptionType` and the *length* of `scopes`, so no token is ever in reach of the UI. Two things it deliberately does *not* do: spawn `claude --version` (seconds of Node startup to fill in a label; the installer's version store answers it for free, and an npm install honestly reads "—"), and show the identity by default — the holder, the email and every absolute path are **masked** (initials, `a•••••@example.com`, paths folded back to `~` / `%LocalAppData%`) because this is precisely the page that ends up in a screenshot attached to an issue; one button reveals and re-hides them, and **Copy for a bug report** copies the page as plain text *exactly as displayed*, so a masked holder stays masked in the clipboard. A personal account with no organization collapses that row instead of dashing it, and a machine with no OAuth account at all (API key, Bedrock, Vertex) gets one explanatory card instead of eight rows of "—". 51 new keys across all five `lang/*.json`; `--settings System` opens it standalone for the preview loop. Two bugs the screenshots caught before shipping: the native installer's version entries are **files**, not directories (`GetDirectories` found nothing, so the version read "—"), and `installMethod` was being title-cased into "Native" when it is a literal token Claude Code's own config calls `native`.

## Block L — Scan resilience

- **T109** — `SafeWalk.cs`: one unreadable directory can no longer blank the app. Reported from the field as *"couldn't build the report: the path cannot be traversed because it contains an untrusted mount point"* — a `memory` junction inside `~/.claude/projects` that Windows' Redirection Guard refuses to traverse, which aborted the framework's `AllDirectories` enumeration and with it the **entire** Statistics window: no charts, no numbers, just the error. The same single point of failure sat under every local scan (`UsageReport.ScanTokens`, `UsageInsights`, `ActivityProfile`, `ContextUsage`, `TranscriptTail` and the recursive `ContextScanner` helpers), so a denied ACL, a session folder deleted mid-sweep or a path past MAX_PATH anywhere under `projects/` cost the user everything downstream of it. The walk is now per directory, so a failure is scoped to the subtree that caused it. Three things the naive version gets wrong and this one doesn't: entries are **materialized** (`GetFiles`, not `EnumerateFiles`) — the `try`/`catch` wrappers the codebase already had around lazy enumerables caught *nothing*, because the IO happens later inside the caller's `foreach`; a reparse point is **replaced by the path it names before anything opens it**, which both sidesteps the blocked traversal (opening the real directory is allowed — only going *through* the link is refused) and walks a shared target once instead of once per junction (this machine has three pointing at the same `_turing-shared\memory`); and children come back as `DirectoryInfo`, whose attributes the enumeration already filled in, so detecting those reparse points costs no extra syscall — ~46ms vs ~34ms over 600 transcripts, and a fresh context scan 95ms vs 73ms. Verified against a hostile fixture (a junction plus a directory with read denied by ACL) where the framework walker throws and the walk returns every readable file exactly once, and against the real tree for equivalence: the `--context` report is identical line for line, 969 files across 35 projects, and the Statistics window renders in pt-BR. Depth cap plus a visited set for the junction-pointing-at-its-own-ancestor case. No user-visible strings — the fix is that the existing ones stop appearing.
