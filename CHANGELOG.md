> just a searchable map of *what* shipped and *where* the rationale lived. Implementation detail is
> deliberately removed from [ROADMAP.md](ROADMAP.md) once a task ships.
>
> Maintenance: `roadkeep ship <id>` writes the entry here, clears the roadmap line and drops the
> rationale section, all three or none of them. `roadkeep record` is the door for a fix nobody
> planned. This file is not hand-edited; the `roadkeep` skill says which command to call.

> [roadkeep.toml](roadkeep.toml) declares both absences once, instead of on all 163 lines.
>
> **Blocks A–H were reconstructed from the git history** (110 commits, v1.0.0 → v1.4.6) when this
> ledger was introduced, so their T-numbers are retroactive: one entry per shipped *unit of work*,
> not one per commit. Block I onward is numbered as it happens.

## Block A — Foundation (tray, icon, API, projection)

- **T1** — WinForms tray shell: `NotifyIcon` + `ApplicationContext`, with the usage number drawn as a GDI+ **vector** (`GraphicsPath` + outline) at the real `SM_CXSMICON` size under `PerMonitorV2` DPI awareness — never a downscaled bitmap. (`47dae10`)
- **T2** — `ApiClient`: OAuth token read from `~/.claude/.credentials.json`, `anthropic-ratelimit-unified-*` headers parsed into the 5h / 7d / extra windows. (`47dae10`)
- **T3** — `BurnTracker`: utilization history → least-squares slope → exhaustion projection (`Projection.Ok`/`Danger`/`Unknown`). (`9577a0c`)
- **T4** — Projection-driven icon color: the fill bar turns red when the window is on track to run out before it resets. (`9577a0c`, `30a9e79`)
- **T5** — `UsageInsights`: last 24h of `~/.claude/projects/**/*.jsonl` aggregated into a cost-weighted breakdown (subagent share, >150k-context share, per-model split) behind the "Usage insights" submenu and `--insights`. (`9577a0c`)
- **T6** — Single-instance enforcement via a named mutex; a second launch exits silently instead of adding a second tray icon. (`9577a0c`)
- **T7** — Multi-resolution app `.ico` generated from the same GDI+ logo renderer (`--makeicon`), plus the `--render` / `--social` dev helpers. (`9577a0c`, `bea59a3`)
- **T8** — Icon legibility pass: text fitting, glyph centering and scaling verified at 16 / 20 / 32 px. (`849a576`, `ad2ec09`, `8f282b7`)
- **T9** — Last-refresh timestamp in the tooltip; and red (not green) once a window sits at 100%. (`a611198`, `a0b6176`)
- **T280** — **The tooltip now dates the spell, not just the state.** While extra usage is paying it reads "paying since 3h 20m", measured from the first reading past the included quota — and says nothing at all when the crossing is not on file, because the store's own beginning is not an event. Last rung of the fitting ladder, so it is the first line dropped: at the 127-character cap pt-BR gets it in both billing states, en and es in one, fr in neither.
- **T293** — **A switch is one assignment now.** Everything held about the followed account lives on `MonitoredAccount`, replaced where `RefreshWatched` already detects the icon changed hands — so a route that switches without a click gets it too. Building it found three fields nobody had listed, two of them live: a leftover error count drew a red icon on an account whose polls had never failed, and a leftover auth latch suppressed the sign-in prompt on the account you switched to in order to sign in. `--selftest` reads the source and fails a second assigner.
- **T302** — **A third rung, and it has no words in it.** `← 3h 20m` costs 8 characters in every language because there is nothing in it to translate, so fr now says how long in the state that is actually spending and es in the one that is not — five of five languages reach it somewhere, against three before. Two of ten states still drop it, both with under six characters free. The arrow is asserted never to be `⟳`, which means time remaining.
- **T303** — **A poll now attributes its reading to the account it started on.** The account is captured before the fetch await and compared after it: on a mismatch the screen, projection, alarm and toasts are refused, and the reading is filed under its own key rather than dropped — it cost quota, and `usage-history.jsonl` cannot be rebuilt. `RecordReading` makes that key a parameter for all three callers, and `--selftest` fails both a missing guard and any line keyed on the live monitored profile.
- **T304** — **One poll per account, and the gate lives on the account.** A tick arriving mid-poll is skipped, a click is remembered and run when the poll lands, and a switch needs no rule at all — the incoming account arrives with the flag clear, because T293 replaces the whole object. So the refresh interval is a ceiling on API calls rather than an average, and one reading can no longer be appended twice seconds apart into the store that folds into a permanent aggregate.
- **T306** — **All ten billing states now say how long, and the measurement chose the rule.** Where the duration would otherwise be silent, the bounded window the icon is not about — the one T215 already sheds, and the one the display setting did not choose — is given up for it. Both brakes are asserted: never where a rung already fitted, and never to buy the wordless form. en and fr each traded a percentage and got the full sentence; the two states that showed the glyph kept both readings.
- **T307** — **The fitter is asked instead of predicted.** The projection line is committed before the shed decision, so `SpellSurvives` measures the room actually left on the lines and the duplicated "first rung that fits" walk is gone — a third projection rung can no longer leave a confident wrong answer behind. Verified by diffing all fifteen billing compositions in five languages: byte-identical. The residual is stated rather than left: the projection now picks its rung before a shed frees room, so a translation whose full form straddled that room would keep the unscoped sentence.
- **T321** — **The digits now say which window their number is about.** White for the 5h session, a light yellow for the 7d week and orange for extra usage — the digits' fill being the one attribute on the tile that §XI.3's rule had never spent — judged on --render's new scope sheet at 16px over every bar colour, with --selftest holding the three apart and an unspelled scope falling back to cream.
- **T322** — **The number's colour is now readable at the size the tray draws it, and it states the account rather than a menu pick.** Both inks are resaturated after being chosen on an 8x sheet that now carries a real-16px band beside it, and orange means billing whichever window the figure is about — stopped keeps the window's own colour, because orange says paying.
- **T310** — One clay, declared once. Brand.cs holds the three bytes and one conversion per edge - GDI+ Color for the tray icon, a frozen WPF Brush for the charts and the markup through x:Static, the band alpha, and the hex string the toast palette takes - because a WinForms icon and a WPF chart can share a value and never a brush. The count in the design was eight and the reading found twelve, one of them added by T288 four days after the line was written, which is the drift arriving while the task about it sat open. The check moved onto the value rather than onto whichever surface happened to be assertable: it used to pin the toast palette to a literal hex, holding one of twelve still while eleven were free to move. Now it asserts both conversions against the bytes and fails a second spelling anywhere under src - and on its first run it reported itself, because the needles were literals; they come from Brand too now.

Matched on the path and not the process name, so a Debug tray does not block a Release publish. It never stops that process: the tray is the user own running app, and a build script that kills applications is worse than one that asks. Demonstrated on the real tray, both directions.
- **T269** — A completed build now sweeps the temp projects the WPF SDK leaves behind, so the folder stops drifting into the state where the documented dotnet build refuses with MSB1011 - one had sat in this root for four hours, gitignored and therefore never mentioned. Age-guarded on purpose: parallel sessions share this tree, a temp project younger than ten minutes may belong to a build running now, and an unguarded delete would have made the missing-generated-file failures worse rather than better. What the sweep cannot do is recover from the state, because MSB1011 is raised before the project is loaded, so that one line went to AGENTS.md instead.
- **T270** — The two build failures that are not your code are named where the command is, both measured: MSB1011 is a killed build leaving a temp project, and a missing generated file is the WPF markup pass racing the IDE design-time builds over one obj directory - three dotnet worker nodes and two IDE language servers were sharing it, which is what T258 and T269 had guessed was a parallel session. Both mitigations were tried and rejected by measurement: Directory.Build.rsp is not honoured by dotnet build and MSBUILDDISABLENODEREUSE leaves nodes alive, and node reuse buys no measurable time here anyway - 9s either way. So the deliverable is the sentence plus a non-goal, and never a retry loop.
- **T341** — The four single-file properties are Release-only, so a no-op Debug build fell from 81-395s to 1.2s and bin\Debug from 155.6 MB to 1.9 MB, with the published .exe byte-identical either way.
- **T349** — The SDK patch is named in global.json and nowhere else: all three setup-dotnet steps resolve through it, so a tag rebuilds to the same .exe, and --selftest reads the workflows and fails a fourth step that names its own version.
- **T350** — Measured, and the pin holds through both compilers: two clean Release publishes on the pinned SDK produced one .exe (75,882,190 bytes, SHA-256 C0D8C245...969D), and two Inno Setup 6.7.3 compiles of that .exe produced one installer (70,589,578 bytes, SHA-256 5E7E1577...A41F) - so the InstallerSha256 update-winget.ps1 writes into every manifest is reproducible from a tag, and T349 is closed rather than assumed.
- **T351** — ReleaseDate now comes from the commit being packaged rather than from the clock - the tag for that version, the HEAD behind it, then the clock, with the run naming which answered - so regenerating v1.6.2's manifests today reproduces the four published files byte for byte instead of redating them to the day the job ran.

## Block J — Activity-aware pacing

- **T86** — `ActivityProfile.cs`: a weekly activity *shape* — 168 buckets (day-of-week × local hour) holding `p(active)`, the recency-weighted share of observed weeks in which that hour saw at least one request. Built from `~/.claude/projects` timestamps because `usage-history.jsonl` is pruned at 8 days and structurally cannot see other weeks; only timestamps are read, not even token counts. Weeks are the rolling windows `[now−7(w+1)d, now−7w d)`, so every week contains each bucket exactly once and no partial-week correction is needed. Two anti-overfitting guards: 0.8/week exponential decay (half-life ≈3 weeks) and a blend toward the user's own flat active-rate prior worth 1.5 weeks of evidence, so a single holiday week cannot claim nobody works on Wednesdays — on the dev machine's 6 weeks that puts a 7% floor under the sleeping hours rather than a zero, which is the honest reading given usage from another machine leaves no local transcript. Presence per bucket, not request counts: one frantic afternoon must not outvote five ordinary ones. Cached at `%LocalAppData%\ClaudeTray\activity-profile.json` (~1.5 KB, 168 rounded floats) and recomputed after 20h; a cold scan of 93,856 requests across 6 weeks takes ~15s, which is why it is a daily cache and not a per-open scan, and it uses substring tests rather than `JsonDocument.Parse` per line. `ExpectedActiveHours(from, to)` — Σ p over the hours a span covers, pro-rating both ends — is the accessor T87 will spend quota against. The entry stores the **absolute local hour** (`local.Ticks / TicksPerHour`, converted at scan time so the historical UTC offset and DST are the ones that applied then) plus a count per hour, and the week is derived at aggregation time in the one place both paths share, so cached and full-sweep results cannot drift. Nor is the 12-week cutoff applied to individual lines any more: the entry describes the file rather than the moment it was scanned, so it stays valid as the window slides, while the file-level mtime check keeps out-of-window transcripts from being opened at all and bounds the cache to the current window. The cache is shared across profiles rather than stored per profile, for the same reason `context-usage.json` is — entries are keyed by absolute path plus fingerprint, so two profiles pointing at one tree share the work instead of repeating it. Three modes keep it honest: `--activity --refresh` re-reads every transcript (without which a cache bug is unfalsifiable) while still leaving the cache warm, and a `--root` fixture tree neither reads nor writes it (T128's rule). `--activity` now prints what the sweep cost — transcripts in window, how many were actually opened, MB read — so the cache is visible rather than merely fast. Verified by diffing the printed grid across cold, cached and `--refresh` runs: identical in all three, and a synthetic fixture lighting only local hours 09/10/14 comes back as exactly those buckets. Internal: no user-facing surface.
- **T93** — The projection prefers the *measured* week once there is enough of it. The transcript grid has a structural blind spot the UI had to apologise for — usage from another machine or from claude.ai counts against the same limit and leaves no transcript here — while the folded aggregate (T88) is built from the rate-limit utilization itself and counts every request whoever made it and wherever. So the measured grid stops being a second opinion to validate against and becomes the better source. Blended **per bucket**, never switched wholesale: `HourlyUsage.MeasuredProfile` now also returns the decayed weeks of observation *per hour*, and each bucket takes `w = min(1, observed / 3)` from the store and the rest from the transcripts. Hours the store knows well come from the store; hours it barely saw — and every hour on a machine that has just started folding — stay with the transcripts, which keeps their two remaining jobs (bootstrapping the first weeks, and covering hours the app wasn't running to observe). A linear ramp rather than a cutover at three weeks, which would visibly jump the projection on an arbitrary day. The blend is applied on every read and deliberately **not** cached: what is cached is the transcript grid, which only changes when the transcripts do, while the measured store changes every day the tray runs — so `WriteCache` happens first and `BlendMeasured` second. `Confident` now reads the *larger* of the two coverages, since a machine with thin transcripts but weeks of folded readings knows its own week perfectly well. Two consequences handled rather than discovered: `--activity --measured` now diffs the measurement against the **inferred** grid rather than the blended one (comparing it with a grid it is already part of would be marking its own homework), and the method note stops disclaiming the blind spot once the grid is mostly measured — a stale disclaimer is its own kind of wrong — via a new `stats.methodNote.shapeMeasured` across all five `lang/*.json`, plus the matching README paragraph. Verified numerically against one folded day (Friday, covered 15:00–21:00): exactly those seven buckets moved, each to `⅓·measured + ⅔·inferred` (71→47 where the hour was covered but idle, 71→81 and 57→71 where it was active), and every uncovered hour was left untouched — an unobserved hour must never drag the grid toward zero. `--activity` prints the blend share, the folded days behind it, and the per-bucket weight at the widest gap.
- **T94** — The projection stops treating every active hour as costing the same. `p` says *whether* an hour is worked; nothing said what it costs, so a morning of agent work and an evening of one-line questions were paced identically — a bounded error (the rate is calibrated on this window's own average) but a systematic one, and it under-projects exactly the week whose remaining hours are the heavy kind. `HourlyUsage.MeasuredProfile` now also returns the mean spend per *active* hour per bucket, divided by the mean over every active hour, so it is unitless and a week that simply spends more moves no bucket; `ActivityProfile.I` carries it and `ExpectedIntensityHours` sums `Σ p·i` beside the old `Σ p`. Only the folded store can supply this — the transcript sweep deliberately records presence and never reads token counts — which is also why intensity is applied on every read rather than cached: it moves with the store, not with the transcripts. The unit of the projection becomes an *ordinary* active hour, so the measured rate is divided by the elapsed span's own mean intensity (`RatePerOrdinaryHour`) before being multiplied back into `Σ p·i` — calibrating in one unit and spending in another would have introduced a bias larger than the effect. It degrades exactly: with a flat grid every factor is `1.0`, which is exact in IEEE 754, so the arithmetic is the T87 one unchanged — including on a machine with nothing folded yet, where `HasIntensity` is false. The same two anti-overfitting guards the grid itself uses, and they do visible work: shrunk toward 1 by 2.0 weeks of prior and clamped to [0.5, 2.0], the dev machine's single folded day turns a raw 0.31×–1.81× spread (six hours, one observation each) into 0.77×–1.27× — a single 3am incident cannot create a "3am is 4× heavy" bucket. Sequenced after T93 on purpose: intensity is only meaningful once the measured grid is trusted, and two model changes at once would make a regression impossible to attribute. `--activity` prints the heaviest and lightest buckets with the guards that produced them, and `--activity --measured` prints the intensity grid with its own around-1 legend, blank where a bucket has never been observed active — no evidence is not "an ordinary hour", even though the projection has to treat it as one. Internal: no user-facing surface — the same sentence, a better number behind it.
- **T95** — A week away stops teaching the model. Every observed week voted with equal weight (times recency decay), so a holiday voted "these hours are idle" exactly as confidently as a working week voted the opposite — and the flat prior does not address that, because the prior is about *thin* evidence, not *unrepresentative* evidence. `WeeksAway` now measures each week's active hours against the **median** week's and drops anything under 25% of it from both numerator and denominator, in the same currency the grid votes in (presence, never request counts — a quiet week is still a working week). Because the fraction is below 1 the median week can never be excluded, so at least half the weeks always survive; below 4 whole weeks nothing is ever excluded, since with two weeks the median is one of them and "drop the quieter half of what little you have" is how a model convinces itself of a shape it has not seen. The shrink toward the prior now divides by the *voting* weeks rather than every week in range: evidence removed has to weaken the grid, not be quietly replaced by the weeks that remain. `EffectiveWeeks` subtracts the exclusions too, so the confidence gate can't keep drawing a staircase on a sample that no longer supports it. Measured on the dev machine — 6 whole weeks of **71h / 66h / 60h / 71h / 15h / 0h** active: the last two were excluded (median 63h, floor 15.75h), including a week with *zero* active hours that had been voting every one of its 168 buckets idle at full weight. The grid moved from "33% of all hours active, 55.5h in a typical week" to **40% / 67.5h**, and on the `--stats shape` preview the projected landing moved five hours earlier (Aug 4 01:06 → Aug 3 20:03) — the sixth of the shape a fortnight off had been silently subtracting. `--activity` prints the exclusion whether or not it fired, with the median it was measured against, and a fresh scan also prints the per-week active hours with the dropped ones starred — "2 weeks excluded" is unfalsifiable without the weeks it dropped (the standard T92 set for its sweep cache). Grid cache bumped to **v2**: a v1 grid was built without the exclusion and would report "0 weeks excluded", which is a claim about the evidence rather than a missing decoration — the sweep cache survives the bump, so the forced rebuild costs only the sessions that changed. Deliberately not extended to the measured grid (T88/T93): its weeks have unequal coverage, so a low-activity week there is ambiguous between "away" and "the app was closed", and guessing would destroy the very distinction that store exists to preserve. Internal: no user-facing surface.
- **T96** — `--selftest`: the pacing and live-rate arithmetic asserted over synthetic inputs, exiting non-zero on failure. Both blocks introduced properties that are cheap to assert and expensive to lose, and every one of them had been verified exactly once, by a human reading a chart or a CLI dump — nothing stopped an edit from breaking one silently. **58 checks, 2.3s**, in five sections: the staircase (a flat profile reproduces the straight average-pace line to the last bit, at three different p — which is also T94's degradation claim, since a flat intensity grid must make every factor it introduces exactly 1; `Σ p` over a week equals the sum of the grid; `Σ p·i` equals the dot product; a thin profile refuses to shape anything; weeks away are subtracted from the confidence gate), the advice (never proposes an hour whose projected close exceeds `AdviceTarget`, and never proposes an hour the user does not work), the stores (folding the same readings twice spends the same, a day's spend is the sum of its positive deltas, the ghost stays hidden under both of its gates, a ~50× incident is capped at the clamp rather than believed, a near-zero hour is shrunk back toward ordinary rather than clamped, an hour observed but never active stays exactly 1.00×), the sweep (two away weeks out of `[40, 40, 40, 5, 0]` active hours are excluded against a median of 40, the median week is never excluded, at least half always survive, and under 4 weeks nothing ever is), and the tail's byte cursor (a half-written line is held until its newline, completing it releases exactly one turn, an append costs only the appended turns, and a truncated file restarts without re-reporting what it already had). The rate kernel is pinned to its **closed form** rather than to "about right": a sustained R reads as `R × (1 + 1/60)` — the triangular window summed over discrete seconds has gain `(W+1)/2`, not `W/2`, so the 1.7% is arithmetic and not drift — a burst starts at its full weight, decays exactly along the line, and reaches a **true zero at exactly 60s** (the smoothing is attack-only, so a fall passes through untouched), and two projects' rates sum to the rate of both together. No test project and so no third-party framework, which the zero-dependency rule (§I.3) forbids for a repo whose single self-contained `.exe` is a feature: this ships inside the same binary, costs nothing at runtime, and the build workflow now runs it against the very `.exe` it is about to package — a failed check stops the build before an installer exists. Everything it touches is synthetic and removed afterwards: a temp transcript tree and a `selftest` profile directory, never a real profile's stores (T128's rule). Verified to actually bite by mutating `AwayFraction` to 0.001 and watching it fail with the weeks it dropped printed beside the median it measured them against. `--selftest --quick` skips the tail section, which waits on real sweeps. Internal: no user-facing surface.
- **T271** — The read-out named a heaviest and a lightest hour that cannot be found in the only picture it draws. Measured, not eyeballed: the grid Sunday row was 13 light cells then a run of mid cells, with 16:00 and 22:00 both the same glyph, while the line beneath called one the heaviest Sunday hour (2.00x) and the other the lightest (0.79x). Not a wrong number - the grid draws P, the share of weeks an hour was active at all, and the line draws I, how hard it is worked when it is. The control that proves the gap is real is the busiest-bucket line, which IS on the grid axis and does point at its darkest cell (Monday 22:00, the only full-black glyph). Of the three shapes the task allowed - a second grid, a legend, or one clause - this is the cheapest that closes it: the line now opens with intensity, then names the axis it is not. - **T287** — The fold keeps a bit an hour for the spell, written even where nothing was over so its absence still means a day folded before it existed, and a pruned week is no longer a ceiling.
- **T296** — Coverage and the spell are counted for every reading the fold sees, its oldest included, so an hour observed once reads as observed rather than unknown; only spend still waits for a pair.

## Block K — Live throughput

- **T97** — `TranscriptTail.cs`: a byte-level tail over `~/.claude/projects/**/*.jsonl`, so a turn that lands is noticed within ~250ms for the cost of the bytes it appended. A per-file cursor that only ever advances past a newline, a `FileSystemWatcher` as the fast path and a 3s sweep as the floor — the watcher is a hint, not a guarantee (its buffer overflows, and it can error out), and a missed event must cost latency, never freeze the feed. The two named failure modes are handled rather than discovered: a **shrunk** file resets its cursor to zero instead of seeking past the end, and a **partial last line** is held back until its newline arrives instead of being parsed as garbage and lost — both verified against a synthetic root, along with per-project attribution. First sight of a file reads back a bounded 256 KB tail so a consumer starting mid-burst has a rate immediately; anything older than the 300s freshness floor is discarded. Parsing is `UsageReport.TryParseSample`, now shared rather than duplicated, so §I.1 holds by construction. Measured on the dev machine: 602 transcripts per sweep in **17ms** (metadata only — a file untouched since the floor is never opened) and 21 KB read across 40s of two live sessions. Found and fixed on the way: Claude Code writes **one line per content block** of a single API response, each repeating that response's `usage` verbatim, so counting lines counts a thinking-plus-tool-use turn twice — the tail dedupes on `requestId` (falling back to `message.id`), pruned to the freshness window. Internal: no user-facing surface; `--tail [seconds] [--root <dir>]` prints turns as they land plus what the sweep cost.
- **T98** — `LiveRate.cs`: the rolling rate that sits **beside** the window average, never instead of it. Non-cache-read tokens/second over a trailing 60s, fed by the tail and recomputed on a caller-driven tick rather than on an API poll — no timer inside, which is what lets T99's strip stop dead when the window is hidden and keeps the decay honest (a rate recomputed only on arrival holds its last value forever through a pause). The window is **age-weighted**, and that is the whole design: a plain rectangular window was built first and measured wrong in exactly the way this metric must not be — one 60k-token turn pinned the display at 1,000 tok/s for a full minute after the work stopped, then dropped to zero in a single step. A triangular kernel (full weight at the current second, zero at the far edge, weights summing to `W/2` so sustained work still reports its true rate) makes a pause decay from the moment it starts. Smoothing is **attack-only** — a large turn arriving in one second is eased in with an 8s first-order lag, but downwards the rate follows the window exactly, so it reaches a true zero 60s after the last turn instead of being snapped there from whatever the lag left behind. Verified against a controlled synthetic burst: eased attack to a 1,415 tok/s peak, then 1200→1000→800→600→400→200→0, linear and exact. Cache reads are excluded from the headline for the same reason `WindowPace` excludes them, and exposed separately rather than silently — on real traffic that is ~30,000 tok/s of cache read against ~150 tok/s of real work, a 200× ratio that would have drowned the signal. `Quiet` deliberately means "no local turn landed", not "the user is idle": usage from another machine or claude.ai leaves no transcript here. Internal: no user-facing surface yet; `--live [seconds] [--raw] [--root <dir>]` prints the rate once a second with the trailing-window split, labelled *throughput, NOT quota*.
- **T99** — The throughput row moves (`LiveStrip.cs`). The static stacked mix bar under each chart becomes a **strip of the last three minutes** — one column per second, entering right and leaving left, keeping the input/output/cache-create split — with *"Now ≈ 870 tok/s · 52.0k tokens in the last 3 minutes"* above it. The window average, the charts, the verdict chip and the legend are untouched: this is a row, not a re-timing of the pace report, and the two numbers are deliberately adjacent because they answer different questions. Motion at 1 Hz without per-frame work: the geometry is rebuilt once a second (three `StreamGeometry` layers, one per token type) and a single `TranslateTransform` is animated from one column-width to zero over that second, so the rebuild's one-column jump and the slide cancel exactly and the strip scrolls continuously. Every consequence of "the motion is the data" is enforced rather than assumed — **nothing running ⇒ nothing moves** (an empty strip is cleared once and then left alone; no spinner, no breathing pulse, which would imply activity during idleness), **hidden ⇒ stopped** (both `IsVisibleChanged` and `StateChanged`, since a minimized WPF window still reports `IsVisible`), and the tail is owned by the window so a closed Statistics window watches nothing. A non-zero second is floored to one pixel — a single small turn is information and must not round to "idle". The method note gains a sentence: an empty strip means no turn landed *on this machine*, never that nothing is running. Five new keys across all five `lang/*.json`; the window grew 60px for the taller row. Verified by screenshot in English and pt-BR, against the real tail and against `--stats live` / `--capture-stats … live`, which feed a deterministic synthetic three minutes so the published image is reproducible; the published `docs/statistics-*.png` were regenerated.
- **T100** — Which project is burning it. The strip stacks **per project** and the live row says how many sessions are active, which across five repos is the question actually being asked — not *how fast* but *where*. Attribution is free: the transcript path already names the project. Deliberately **adaptive** — with two or more projects generating, the stack is per project; with one there is nothing to attribute and the by-type mix stays, because folding a single-project strip to one flat colour would lose the input/output/cache-create split for nothing. A session counts as active on a **turn in the last 2 minutes**, not on file presence, or every terminal left open all week would inflate the count. Palette run through the data-viz validator rather than eyeballed: four categorical hues in fixed order (blue/orange/aqua/yellow) plus an achromatic residual, validated as a stack against both themes' surfaces — worst adjacent CVD ΔE 9.1 light / 8.4 dark, worst normal-vision ΔE 20.8 / 16.9, all ≥3:1 contrast in dark. - **T110** — The strip's height means something. Two defects behind one symptom, reported from the field as *"the bars are tiny and sometimes there are numbers"*: the row walked its series from **index 0** of a feed that keeps 300 seconds while the strip is 180 columns wide (`LiveRate.HistorySeconds` > `LiveStrip.Seconds`), so it drew the *oldest* three minutes and clipped the newest two minutes off the right edge — and it then scaled what was left to the tallest bucket in the **whole** feed, which could be a burst that had already scrolled away, flattening everything on screen onto the 1px floor. It now walks backwards from the newest bucket (one extra column laid out past the left edge, so the slide still has something to bring in) and takes its peak from exactly what it draws. With that fixed the scale is also *stated*: full height is the visible peak rounded up to a readable step (1 / 1.5 / 2 / 2.5 / 3 / 4 / 5 / 6 / 8 per decade, so rounding up costs at most a third of the bar height), ruled across the plot at the ceiling and at its half and labelled in tok/s in a 40px right-hand gutter — Task Manager's treatment, and inside the strip so it costs no layout row (§V.9's one constraint). The labels sit on the plate rather than floated over the plot, so they never cover a column, and the rules live outside the sliding layer, because a number attached to something that moves reads as data rather than as scale. The gutter is dropped below 220px of width, the half-mark is dropped when its label would crowd the ceiling's, and the whole axis disappears while the strip is flat — a scale with nothing drawn against it claims a precision that isn't there. Hover says what full height means; the strip grew 44→56px so two 10px labels have room. Resource *references* rather than resolved brushes for the rules and labels, since the strip is built once and outlives a light/dark switch. Two keys across all five `lang/*.json`. Verified against the deterministic `--stats live` fixture and against the real tail — which is where the scale fix earns itself: one 240k-token second (a large cache write) now reads as `250k/s` instead of as an unexplained wall of 1px bars. Published `docs/statistics-*.png` regenerated.

- **T111** — The live strip gets its own tab. Asked in the field as *"the 5h chart is the same as the week one, right? could you make a Throughput tab?"* — and the premise was exactly right about the part that mattered: the charts differ, but the live row (number, strip, per-project legend) has **no window scope**, so "now" was rendered twice, identically, under two different charts. The pace tabs keep both *numbers* — the window average with its type legend, and the one-line "Now ≈ N tok/s" — because the pacing report is where you would miss the live rate, and lose only the duplicated picture; each recovers ~90px in a pane that scrolls. The new tab pairs the strip with a stated time axis (`3 min ago` … `now`, which 56px had no room for) and, under it, **both** window averages captioned by window: same tokens, slower clock, so the fast number has something to be read against. Consequences handled rather than discovered: two `LiveStrip` instances collapse to one (`_stripS`/`_stripW` → `_strip`), the geometry is skipped entirely while another tab is selected (the *number* still ticks on every tab — it is text), a tab arrival repaints without waiting for the next second, and the swatch-suppression rule moves from a global to a per-call-site `besideStrip` flag: the Throughput tab's averages drop their swatches while the strip above them is stacked per project, and the pace tabs — which no longer sit next to anything coloured — keep theirs. `SaveAllTabs` gained a third snapshot (`-throughput.png`), so `--capture-stats … live` publishes the new tab. - **T112** — One second may no longer flatten the minute. Even with T110's honest axis and T111's 220px of height, real traffic has a dynamic range a linear scale cannot hold: measured here, a single turn writing a large cache block lands **~240,000 tokens in one second** beside ordinary seconds of ~2,000, so scaling to the peak put a whole minute of actual work on the 1px floor — a chart that was technically faithful and practically unreadable. The ceiling is now the **95th percentile of the busy seconds on screen**, and the columns that run past it are drawn **broken**: fill stops 4px short, then a 2px cap in the primary ink (not a softer grey — it would be mistaken for the grey "others" series it can sit directly above) says *this continues*. Truncation is from the top of the stack, so every segment keeps its true scale; squashing the column to fit would have misreported all of them. Three guards keep the cut from costing more than it buys: the quantile is taken over **busy** seconds only (including idle ones drags it to zero and clips everything), clipping needs **12** busy seconds (on a sparse strip the few bars are the whole story), and it needs the peak to be a genuine outlier — **2× the quantile** — so ordinary traffic keeps a fully faithful peak-based axis and nothing is cut to buy contrast that isn't needed. Clipping data is a thing a monitor may only do out loud, so the hover changes when it happens: how many columns were capped, and what the busiest second actually carried (singular and plural keys, ×5 languages), and it is rebuilt only when that *text* changes, since the peak moves every second but "240k/s" does not. Verified against the fixture and the real tail in English and pt-BR: with the spike present the axis reads 3k/s and three columns carry caps; on ordinary traffic (peak 7k, quantile 5k) nothing is clipped at all and the axis is the rounded peak, exactly as before.

- **T114** — `LiveRate` reports the headline *as a series*, plus sticky slots. The rate the row prints was only ever available for one instant — "now" — so the picture under it had to be built from the raw per-second buckets, which are **events**: a turn's whole usage lands in the second it finished (the transcript timestamp is the write time), which is why the strip read as spikes separated by holes rather than as a flow. `RateHistory(n)`, `TypeRates(n)` and `Projects(n)` now evaluate the *same* age-weighted 60s kernel at every one of the last *n* seconds, so each point means "tokens/s as it stood then" — a continuous quantity that decays through a pause because the work really is ageing out of the window, and rises when new work lands. That is what makes a line honest here, where joining the raw buckets would have drawn a rate that never existed. The 300s ring turns out to be exactly the right size: every point needs the 60s behind it, so `MaxRateHistory` is 240 — 60s of headroom over the 180 the chart shows. The headline's **attack-only lag is applied along the series too**, so the right-hand end equals the number printed above it (verified live: 305 tok/s at the edge against 305 in the row) — of two numbers that disagree on screen, both lose. The cost is stated where it lives: smoothing the parts is not quite smoothing the whole, so per-project series stop summing to the total *during* an attack, which is why they will be drawn as separate lines rather than stacked. Second half: **`Slot`**, a project's fixed colour/legend position, claimed on first appearance and released only when it has nothing left in the window, with `Projects()` returning slices in slot order instead of by rate. Rate order is right for a snapshot and wrong for a chart — it would swap two lines' colours mid-flight exactly when the busier repo changed. Who fills the four slots is still decided by rate, so a newcomer arriving with all four taken folds into the residual until one frees. `--live` prints each project's slot and, at the end, every series as a sparkline with its last value, so both claims (stable slots, edge equals headline) are checkable without a window; `LiveRate.RateFrom` applies the same kernel to a plain array, which is the seam the `--stats live` fixture will draw through. No user-visible strings: the chart that consumes this is T115.

- **T115** — A project's series stops blinking. Reported from watching the real chart: *"if a session stops for a moment its whole graph disappears, and when it comes back its old history comes back too — so a session blinks over time instead of staying until it ages off"*. Exactly right, and the cause was one word in `Projects()`: membership was tested with `win > 0` — tokens in the **trailing 60s rate window** — while the chart draws **180 seconds**. A repo that paused for longer than the rate window was therefore dropped from the result entirely, taking its still-live history with it, and the next turn brought the whole thing back. `DrawnSum` replaces that test: a project is in the result while it has anything the chart could still draw (the drawn span plus the kernel's reach behind its oldest point), so it now decays toward zero and ages off the left edge like the data it is. Ranking still uses the rate — who is busiest *now* is what decides who gets a slot — so the fix does not disturb T114's stickiness; it is what makes it hold through a pause, which is when a fixed colour is worth having. Callers pass the span they draw (`Projects(LiveStrip.Seconds)`). Proved with a synthetic root rather than by waiting: a project whose only turn is 100s old — outside the rate window, inside the drawn span — now comes back listed in slot 0 with its rise-and-decay intact and 0 tok/s at the right edge, where before it was absent from the result. No new strings; the fix is that existing ones stop flickering.

- **T116** — Bars become **two line charts** (`LiveStrip.cs` → `LiveChart.cs`). - **T117** — The left edge holds still. Reported as *"the start of the chart moves back and forth to a beat, and the tip also drifts up and down — the rest of the chart stays constant"*, which is two defects with the same symptom and both were real. **Horizontally:** the figure ended at the oldest *visible* sample, one sample-width inside the plot, and the 1s slide moved that endpoint across a visible column every second — the newest end never showed it because it starts off the right edge and slides in, so the oldest end needed the same treatment on the other side. - **T118** — A poll no longer blanks the window. Reported plainly: *"the consumption screen refreshes every few minutes, and the Throughput tab doesn't need refreshing — the problem is the whole screen blinks when it does"*. It did, and the cause was one unconditional line: `Reload()` opened with `ShowStatus("computing…")`, which **collapses the entire pane** and shows a status line, then restores it when the background pace computation returns. On the first open that is right — there is nothing to show yet. On the tray's poll (every 5 minutes by default) it threw away a perfectly good screen for a few hundred milliseconds, and on the Throughput tab it was worse than cosmetic: that tab reads nothing from the API, so its live charts were being torn down and rebuilt for a recomputation that belongs to the other two tabs. - **T119** — Drawn is drawn: the right-hand end stops rewriting itself. Reported from watching it live: *"at the end of the chart, when a value rises, the last couple of seconds that were already drawn get remade and behave oddly — what is done shouldn't change"*. Exactly the right principle, and the cause is reporting latency rather than arithmetic: a turn carries the timestamp of the second it **finished**, and the tail reports it up to a few seconds later (its watcher is fast; its floor sweep is 3s). So a late arrival lands in a bucket that is already *behind* the head, and because the chart recomputed the whole series from the buckets every second, the recomputation raised points that were on screen a moment ago — the shape of the last two or three seconds kept being rebuilt. `LiveChart` now keeps its own history and only ever **appends** the newest sample to it: a point takes whatever the rate was when its second was drawn and never changes again. The full series is adopted wholesale only when there is nothing to append to — first render, a changed series set, or a gap in the clock (a hidden window stops it) — which is also what fills the chart with the three minutes that preceded the window being opened, so nothing was lost by freezing the rest. A re-render of the *same* second (a resize, a tab switch) redraws the frozen history rather than importing the recomputation, or a window resize would have pulled the rewritten past back in. The cost is stated instead of hidden: tokens whose report arrives late are counted from the moment the app learned about them, not moved backwards into a second already on screen — which is what every append-only monitor does, and the alternative is a chart that edits its own history. `LiveRate` deliberately stays a faithful recomputation, so `--live`'s `worst redraw drift` still measures the underlying instability: **40.67 tok/s** against live traffic on this machine, all of it now absorbed by the chart layer.

- **T102** — One API response, counted once, in every local scan. Claude Code writes **one `assistant` line per content block** — a thinking block and two tool calls are three lines — and each repeats that response's `message.usage` verbatim under the same `requestId`. The burn-up curve hid it because it is rescaled to the live utilization, which fixes the endpoint and not the **shape**: hour-by-hour, the share of the window each hour carried moved by up to **0.64pp** (4.06% total variation) once counted correctly — the same samples `WindowPace.MeasuredActiveHours` and the projection are calibrated against. `UsageReport.ScanTokens` now keys on the id the parser already emits (`requestId`, falling back to `message.id`), with the set **global rather than per file**, which also drops the copies a forked or resumed session inherits from its parent transcript; a line carrying neither id is still counted, since it cannot be told apart from a genuine second response and over-counting once beats dropping real spend. `UsageInsights` had the same defect and is fixed the same way — before/after on the same 24 hours: **5,763 → 3,370 requests** (−41.5%, matching the line measurement) and the ">150k context" share moving **75% → 77%**, a user-visible number that was skewed by exactly the mechanism above. `ActivityProfile` is the one reader that needed **no** change and now says so in a comment: its grid records *presence* ("this hour saw work"), so a repeated line sets a bit that is already set — only its `Samples` counter saw them, which is why `--activity` now reports "assistant lines" instead of miscalling them requests. Internal: no user-facing surface, no new strings — the visible effect is that existing numbers are right.

- **T103** — The sweep stops walking all of history every 3 seconds. `TranscriptTail` enumerated every `*.jsonl` under `~/.claude/projects` on **every** sweep — metadata-only and individually cheap, but O(all history), running twenty times a minute for as long as the window is open, and growing forever. §V.8 offered two fixes and named the directory-mtime one as the cheaper to try first; measuring it **killed it**: on NTFS a directory's mtime moves when an entry is added, renamed or removed and **not when a file inside it is appended**, which is precisely the case that matters — a live session appends to a transcript that already exists, so the "changed directories only" walk would have gone blind exactly while somebody was working. (Recorded in [AGENTS.md](AGENTS.md), since the idea is an inviting one to have twice.) So the other fix: the `FileSystemWatcher` already knows *which* file changed and was throwing that away, and its paths are now the sweep's **work list** — a cheap sweep looks at those and nothing else. The full walk survives as **reconciliation** every `ReconcileMs` (30s), which is the whole safety argument: a dropped event costs up to 30s of latency and can never strand a file, a watcher that died (`_watching == false`) forces *every* sweep to be full again, and a renamed file is announced under both names so the old cursor is retired rather than left pointing at a path nobody will visit. The same reconciling pass now **prunes cursors** for files untouched since the freshness cutoff — they accumulated one per transcript ever seen, and re-priming one later is safe because everything the prime reads back is already past the 300s floor (and `_seen` covers the clock-skew edge). Measured against the real tree, 544 transcripts: a full sweep **69.31ms**, a cheap sweep **0.05ms** — 19 sweeps in 40s of which **2** were full, so the walking drops from ~1.3s to ~139ms per 40s, and the per-sweep cost stops tracking the size of the history except twice a minute. Verified on synthetic roots for the three things this could have broken: a project directory and transcript created *after* the tail started are still found (600-file tree: 18 sweeps, 2 full, every turn reported), a **partial last line** is still held back and reported whole when its newline lands, and with **no watcher at all** every sweep goes full — 8 of 8 — and finds a file nothing announced. `--tail` and `--live` now print full vs cheap sweeps and both timings, so the claim is checkable rather than asserted. Internal: no user-facing surface, no new strings.

- **T104** — A second you can point at. T110 gave the charts a magnitude, T111 the height to use it and T116 lines you can follow, which left the one interaction a time-series should not ship without: they answered only in shapes. Five keys across all five `lang/*.json`; the fixture pins the reading on its deliberate cache write (47k tokens landed in one second, drawn as a rate that spreads them over the following minute) so the published screenshot shows the interaction a capture has no pointer for, and `--stats live` now opens on the Throughput tab — the same reasoning `--stats shape` uses to open on the weekly one. - **T105** — One reader of the slug encoding (`src/Core/ProjectSlug.cs`). A `projects/<slug>` name is the session's root path with **every non-alphanumeric character replaced by `-`**, which is lossy in the way that matters: a separator and a literal hyphen encode identically, so `claude-tray` and `claude\tray` produce the same slug and `…-shio-2026-3` naïvely reads as the folder "3". §V.10 counted two readers of that encoding; the code had **three**, and the third is the reason this is more than tidying — `ContextFixture` replaced only the colon and the separators, an approximation that agrees with the real encoding right up until a fixture path carries a dot or a space, at which point the fixture writes a directory name Claude Code would never write and the project silently fails to resolve. Internal: no user-facing surface, no new strings.

What comes back is the **pace panes only**: the entry is read after the live tail has been reset, never restoring the drawn live history, which appends by construction (T119) and is the third defect T164 fixed. A cache keyed by profile cannot show one account under another's name — and the path it changes is precisely the one T165 asserts, so `-Case Profiles` re-run against it still walks *Pessoal → Trabalho → Pessoal* and reads 28% both times. Closes Block AA; `--selftest` unaffected at 134/134, no new strings, no UI change beyond the blink being gone.

- **T164** — **Coming back to a profile shows that profile again.** Reported from use: *"se eu visualizo o gráfico de consumo de um perfil, mudo para outro perfil no combobox e volto para o perfil anterior, o gráfico muda — parece que quando mudamos o combobox ele não zera corretamente os dados"*. ## Block V — What the self-check found

- **T153** — The two properties `--selftest` was partly built for, and did not assert, are asserted. Both were named in §IV.12 as reasons to write the checks at all, and both were unreachable for a mechanical reason rather than a hard one. **The tail's primed offset**: every transcript fixture is a few hundred bytes, so `fi.Length - PrimeBytes` was always ≤ 0, the first sweep always started at offset 0, and `NeedsAlign` — the branch that skips a resumed cursor forward to a line boundary — had never once executed inside a check. The new fixture is a 317 KB transcript built **by byte offset** rather than by line (`\n` only; `WriteAllLines` would write CRLF and the arithmetic would describe a different file from the one on disk): 200 old turns as bulk, then enough fresh ones to overfill the 256 KB window by 4 KB, so the prime offset lands *inside a fresh turn* — which is what makes the assertions sharp rather than decorative. Each turn carries its index as its `input_tokens`, so a reported sample says which line it came from; the assertions are on the min and the max of the reported set rather than on its first and last element, because the sweep sorts by timestamp and these turns share a second, so their order is not defined. Six checks: the straddled turn is dropped and the next one is not, every turn after it arrives exactly once, nothing behind the window arrives at all, the sweep reads **exactly** `PrimeBytes` of a 317 KB file, and — the one the flag alone can break — an append after a primed read is not re-aligned away, which is what asserts `NeedsAlign` is cleared. **The rate's zero-fill**: `LiveRate.Add` was private and reachable only by standing up a real `TranscriptTail` and waiting for a sweep, so "a paused caller resumes with a truthful gap rather than a stale plateau" could not be stated. `Add` is `internal` now — one method on an already-`internal` class, the same visibility the fixtures rely on — so a burst goes straight in and the clock moves by hand: the burst lands at its full weight, a caller paused past the 60s window comes back to a true zero on both the smoothed and the raw reading and reports itself `Quiet`, the burst is still in the 5-minute strip (the strip is not the window), and a caller gone for an hour comes back to an empty strip and no project series at all — the cap on the zero-fill loop, asserted. **Each new check was confirmed to fail before it passed**, against three deliberately broken builds: priming removed (`from = 0`) fails four of them, `NeedsAlign` left set fails the append pair (889 samples where 890 were expected), and the zero-fill loop commented out fails the hour-long-gap pair (1 of 300 buckets still holding tokens). 58 checks at the start of the block, **80** now, 2.7s. Also fixed two stale cross-references while in the files: the project-display-name rule is T154, and two doc comments credited it to T150 — a number that now means something else entirely. Internal: no user-facing change.

- **T152** — A week away no longer teaches the **measured** grid that nobody works those hours. T95 gave the transcript grid an away-week test; the folded store (T88), which T93 blends in bucket by bucket as it earns coverage, still counted every hour of a holiday — so the same week that was dropped from one vote was cast in full in the other, and as the measured share grows that goes from softening the grid to *being* it. T95 deferred it for a stated reason rather than an oversight: a quiet folded week is ambiguous between "the user was away" and "the tray was not running to see it". The store is what resolves it — an hour with no reading is *unknown* and already outside the denominator — so the test is two conditions where the transcript one needed one: a week is judged only once at least **half its 168 hours carry a reading** (`MinAwayWeekCoverage`), and it is dropped only if, being judged, its active-hour count falls under `AwayFraction` (25%) of the **median judged week's**. A week that fails the coverage test is not evidence either way: it is never dropped, never in the median, and goes on contributing exactly what it contributed before. `MeasuredProfile` therefore reads the store into weeks before it reads it into buckets — an away test is a statement about a whole week and cannot be made an hour at a time — and a dropped week leaves no weight behind it, the same way T95's does, so removing evidence weakens the bucket instead of handing its vote to the weeks that remain. `EffectiveWeeks` subtracts the measured exclusions too, so a holiday inside the folded history can no longer talk the confidence gate into shaping a projection. `--activity --measured` prints the verdict per week with its two markers and, deliberately, the coverage it was judged on: `50h/67c?` — 50 active hours, 67 of 168 with a reading, `?` for not judged, `*` for excluded. Printing the coverage is what makes "too little coverage to judge" checkable instead of asserted, and on the dev machine it immediately showed the gate's real reach: with the tray running ~10h a day, weeks land at 67c and 71c and are never judged at all. That is the safe direction (an unjudged week keeps its old behaviour exactly) but it does mean the measured exclusion only fires for a machine the tray watches most of the week. Seven new `--selftest` assertions over a six-week synthetic store, 65/65: the well-covered holiday is dropped, the thinly-covered quiet week is not, the median judged week is never dropped, an excluded week's weight is gone from `Observed` to the ninth decimal while an unjudged one's is still there, under four judged weeks nothing is excluded, and the measured span is subtracted from the confidence gate. Internal: no new user-visible string, no UI change.

- **T151** — The self-check runs on **every push and pull request**, in a `check` workflow of its own. `build.yml` had been the only place `--selftest` ran, and it is `workflow_dispatch` only, so the 58 assertions that guard the pacing and rate arithmetic were evaluated at the moment somebody decided to publish — with an installer half-built behind them. A broken invariant surfaced as *"the release is blocked"* rather than *"that commit is red"*, which is the opposite of why the properties were written down. The new workflow is build, run, done: checkout, .NET 10, `dotnet build -c Release`, then the same `Start-Process`-and-check-`ExitCode` idiom build.yml uses (the app is a Windows-subsystem `.exe`, so its output has to be redirected to be read and its exit code waited for). No secrets, no signing, no Inno Setup, `contents: read`. A **separate workflow** rather than a job added to the existing one, because the trigger belongs to the workflow and not to the job: build.yml must stay manual — cutting a release is a decision somebody makes, never something a push does — and it still runs the check a second time against the packaged single-file `.exe`, which is a different artifact from this one. `dotnet build` rather than `dotnet publish` here on purpose: the csproj is `SelfContained` for `win-x64` either way, so the plain build output is already a runnable `.exe`, and skipping the single-file bundling and its compression is most of the difference in cost (measured on this machine against that exact output: 6.4s build, 4.1s wall for the check, of which 2.3s is the 58 assertions). Two economies: `concurrency` cancels a run that a newer push has superseded, and `paths-ignore` (`**.md`, `docs/**`, `LICENSE`) skips prose-only commits — it skips only when *every* changed file matches, so the repo's usual code-plus-docs commit still runs the check. `branches: ['**']` keeps tag pushes out of it, since a tag is a release and build.yml owns that path. Internal engineering: no README or site change, and the two `paths-ignore` lists are duplicated rather than shared because GitHub Actions does not support YAML anchors — a shared list would silently not be shared.

- **T150** — The live tokens/second reads what it measures. The age-weighted window divided its weighted sum by `W/2` — the integral of the triangular kernel, `∫₀^W (1 − t/W) dt` — while the kernel it actually evaluates is a **sum over discrete seconds**, whose weights come to `Σᵢ₌₀^{W−1} (1 − i/W) = (W+1)/2`: 30.5, not 30. Sustained work at `R` tok/s therefore displayed as `R × (1 + 1/60)`, **1.7% high**, since T98 and in every place the rate is shown — the headline, the strip, the per-project lines, the per-second hover readout. Nobody would have reported it (nobody decides anything on the second decimal of a tok/s reading) and nobody could have seen it on a chart; it was found by T96 having to *state* what a sustained rate should read as, and the check pinned the wrong value as a closed form on purpose so that the day the divisor moved, the assertion had to move with it. The fix is one number, now named once as `LiveRate.KernelSum` instead of open-coded at the four sites that evaluate the kernel (`Tick`, `Series`, `RateFrom`, `WeightedRate`) — the class doc's claim that "the weights sum to what it is divided by" is true again, and it is a `const` a future reader can't retype wrong. Two `--selftest` assertions moved with it: a sustained rate now reads as **itself** (1000 → 1000.000000, not 1016.67), and the burst's opening value is derived from `KernelSum` rather than restating a divisor. Nothing else in the kernel changes — the decay is still exactly linear to a true zero at 60s, and per-project rates still sum to the total, because scaling a linear operator preserves both. 58/58, 2.3s. Not a user-facing change beyond the number being right: no new strings, no layout, no README/site claim was quoting a rate.

## Block U — The environment write stops freezing the app

- **T149** — Picking **Profile ▸ …** or pressing **Save** no longer freezes the tray for seconds. Reported from use: *"quando mudo de perfil no tray a tela trava e não consigo fazer nada"*, and the same on saving an edited profile — a few seconds each time, then normal. The suggested fixes were a loading screen or a different way of writing the variable; neither was needed once the cost was located. Block T's `EnvironmentProfile.Write` ran on the UI thread, and **both** of its halves broadcast `WM_SETTINGCHANGE` to every top-level window on the machine: `Environment.SetEnvironmentVariable(…, User)` sends one itself before returning (no flags, so it waits out a hung window in full) and `Broadcast()` sent a second with a five-second per-window budget. Each sweep waits on every window in turn — measured on this machine, **idle**, at 129 ms to set and 486 ms to remove, and seconds with a browser and an editor open. A tray whose UI thread is inside a broadcast repaints nothing and answers nothing, which is exactly what was reported. So the write is now queued to the thread pool and the caller returns at once; the writes are **chained**, so two quick picks land in the order they were clicked rather than racing for the last word. Measured against the built assembly, driving `Write` directly and timing the *calling* thread: 0.95 ms for an unchanged Save, 0.01 ms for a real switch — against **1,212 ms** the queue then spent broadcasting, which is precisely the time that used to be the frozen tray. That harness earned itself immediately by catching a defect in the first cut of this fix: the short-circuit compared the wanted value against **the registry**, and a queued write has not landed yet, so picking the other profile and picking this one straight back left the machine on the other one — the second click compared against a value that was already stale and dropped itself. It now compares against where the queue is *heading*, falling back to the registry only when nothing is in flight, which is also how a value changed behind the tray's back (System Properties) is still picked up. Two more things fall out of the move off-thread. `Adopt`/`Restore` now return "accepted" rather than "written" — there is no result to await without re-freezing the click, so the ownership bookkeeping is recorded up front, and the worst case if a registry write ever did fail is a settings line claiming a variable the tray does not own, whose only effect is to restore the value already there. And the Save path gets a real short-circuit: `Write` compares against the live value first, so the reconcile `ApplySettings` performs on **every** press — whether or not the profile row was touched — costs one registry read (~0.3 ms) instead of two broadcast sweeps. The tray's own broadcast keeps its `SMTO_ABORTIFHUNG` (that is what .NET's own does not do) with the budget cut 5 s → 2 s, since a slow sweep now delays the *next* switch's rather than the user. `ExitApp` drains the queue, bounded, so switching profile and quitting in the same second cannot lose the variable. No user-visible strings — the fix is that the freeze stops happening.

## Block T — One profile, the whole environment

- **T148** — The **Profile** submenu opens from the keyboard. Found while driving T145's verification through the real menu: every other submenu expands with Right, and this one *closed the menu* instead. The cause was the population point, not the key handling — `_profileMenu` filled its items in `DropDownOpening`, so before the first open `DropDownItems` was empty, and an empty `ToolStripMenuItem` is not a submenu to WinForms: no `ExpandCollapse` pattern, no arrow, and Right handled as "activate a plain command", which dismisses everything. It is now filled while the menu is being built and again in `ContextMenuStrip.Opening`, which already re-read every profile on each open (T137), so the readings are the same poll's and nothing is staler for the move; the settings-save path fills it too, since adding or removing a profile changes its contents. The second reading of the same bug is the automation one: a submenu that is empty at menu-open time cannot be expanded by `Check-Interaction.ps1` either, which is why T142's menu case covered `Open Claude Code` and not this one. That gap is now closed — the harness expands **Profile** the way a keyboard user does (Down to it, Right) and asserts one entry per profile plus the auto-follow toggle, and it was confirmed to *fail* against the pre-fix binary before it passed against the fixed one.

- **T147** — The tray icon says **whose** number it is: with more than one profile registered it wears a thin per-profile colour band along its top edge. Reported from use and independent of the toggle — the number, the fill and the projection colour are identical whichever profile the icon follows, so only the tooltip named it, and with the profile now global "which one am I in?" is the question a glance should answer. §XI.3 left the mark undecided between three candidates, and building settled it against the front-runner: the profile's **initial** was implemented first and rendered at the real 16px, where "P" against "54" or "100" blurs both — the second glyph and the number cannot share the only legible area, exactly as the design section feared, and the number is the thing the app exists to show. The band costs the digits nothing because it lands inside the margin `FitToTile` already leaves above them, so the number is drawn identically marked or not. It is a colour, which §XI.3 flagged as the real risk since colour here means *projection*: what keeps them apart is that they share neither a hue — `Accents` (violet, pink, periwinkle) is disjoint from the green/orange/red of the verdict, the cyan of "no projection yet", the amber of an API error and the slate of the tile — nor a form, the verdict being a level that rises from the bottom and identity a fixed 2px rule at the top, drawn after the bevel so it survives a 100% tile. The slot is the profile's position in the watch list ordered by **key**, not the list's own order: `_watched[0]` is whichever profile the icon currently follows, so indexing that directly would hand every profile the same band the moment it took the icon over — the exact opposite of an identity. Two profiles therefore always differ; a third can re-deal the hues, which is the price of not tying identity to a hash that could collide. One profile gets no band at all (the Profile submenu's own gate), since there is no question to answer and an unexplained stripe would be noise. `TrayContext.AccentSlotFor` is asked by both the icon and `--profiles`, which now prints the band per profile so the mapping is checkable without driving the taskbar. Verified at both ends: `--render` gained an 8×-magnified contact sheet of the real 16px pixels over a light and a dark backdrop (every case, unbanded and once per accent), and the live taskbar icon was screenshotted through UI Automation — a violet band over "76" on the orange fill, the digits untouched.

- **T146** — With **Use the chosen profile everywhere in Windows** on, **Open Claude Code** is a plain command again. The per-profile submenu exists (T123) because a launch used to be the only moment the tray could choose a profile; once T145 puts that choice in the user environment, every entry starts the same session and the menu level asks a question the user has already answered elsewhere. The collapse is a consequence of the new mode, not a feature removed from anyone who did not opt in: with the toggle off the submenu is byte-for-byte what it was, which is half of what the verification checks. What had to survive the collapse is T137's affordance — a profile with no credentials on disk still reads "— sign in" and still runs `claude auth login` — so the collapsed command is **aimed** at the deliberate profile rather than left to inherit; that is also required for correctness, since the tray's own environment block was built at launch and does not see a user-scope variable written after it (`Environment.SetEnvironmentVariable(..., User)` writes the registry, not the running process). It aims at `DeliberateProfile()`, which is null while auto-follow is the thing driving — nothing has been chosen, the tray owns no variable, and inheriting is then the honest launch. The shape decision is one predicate (`TrayContext.LaunchIsSubmenu`) asked by both the tray and `--profiles`, keeping the property T136/T144 established that the two cannot drift about what the menu looks like — which matters here because `Check-Interaction.ps1` reads `--profiles` to know what it should find. That harness was taught the second reason a plain command is correct (it used to report "one profile" for both) and to prefix-match the label, so the "— sign in" variant is not a false failure. Verified by driving the real tray's menu with UI Automation in both modes on a live two-profile machine: toggle on reads nine entries with `Open Claude Code` flat, toggle off expands it to `Pessoal` / `Trabalho` as before. `docs/llms.txt` also lost a claim that T145 had already made false ("the variable is set on the launched process only — never machine-wide").

- **T145** — **Use the chosen profile everywhere in Windows** — the tray now writes the user-scope `CLAUDE_CONFIG_DIR` itself, which is a deliberate reversal of T143. That task refused to (shipping a copyable `setx` instead) because the variable reaches every Claude Code session on the machine and keeps applying after the tray is uninstalled; both are still true, and both are now the requirement — *"preciso que quando eu mudar para um dos perfis, o Windows use este perfil em todo o ambiente"*, VS Code from the Start menu included. Nothing the tray does to a process it launches can reach that, and the three alternatives were dropped for cause (`env.CLAUDE_CONFIG_DIR` in `~/.claude/settings.json` is editing a file inside `~/.claude` — §I.4, no exception; a `claude.cmd` shim on `PATH` reaches *less* and shadows another tool's executable; per-workspace editor settings are not "the whole environment"). What answers T143's objection instead of ignoring it: **what the tray sets, the tray removes** — the previous value is remembered in the tray's own settings and put back when the toggle goes off or the pin is released. Off by default, because an update must never silently rewrite somebody's environment. **It follows the pin, not the icon**: T139 already made a manual pick a distinct, persistent state ("· pinned" + "Resume following"), and auto-follow moves the icon by *observation* — on a machine where a profile is more or less always active, syncing to every icon movement would rewrite a machine-wide setting continuously, which is the very observation that produced T139. The write goes through the same three-way as T144, so choosing the `~/.claude` profile **removes** the variable rather than setting it to a value that would make Claude Code read the wrong `.claude.json` (T136). `WM_SETTINGCHANGE` is broadcast (timed out, so one hung app cannot freeze a menu click) or Explorer keeps the block it built at logon and nothing launched from the Start menu would see the change until sign-out; the row states plainly that programs already running keep the profile they started with, which leaves the "no switching the account of a running session" non-goal untouched. The row also shows the **live** reading of the variable rather than the toggle's intent, so it still tells the truth when something else on the machine set it. Two fields of tray-owned bookkeeping (`EnvironmentProfileOwned`, `EnvironmentProfileRestore`) are exempted from the whole-model write-back for the same reason `Metric` is (T141): a Settings window left open while a menu pick took the variable over would otherwise save "not owned" and strand a value the app no longer knew it had replaced. Verified end-to-end by driving the real tray's menu with UI Automation — the harness T142 shipped — through all three transitions on a live machine: picking Trabalho (`~/.claude`) leaves the variable absent, picking Pessoal writes `…\.claude-pessoal` into `HKCU\Environment`, and "Resume following" puts it back to absent.

- **T144** — Which profile a launch selects is now decided against **what the child process will inherit**, not against `~/.claude`. Reported as *"Abrir Claude Code → Trabalho abre no Pessoal"* on a machine with a machine-wide `CLAUDE_CONFIG_DIR` pointing at the personal profile, and the old rule made that unavoidable: `NeedsConfigDirOverride` answered "no override needed" for `~/.claude` — true only while nothing sets the variable, because the tray then passed nothing and the child inherited the *other* profile's dir. The fix is not "set it anyway": T136 measured that pointing `CLAUDE_CONFIG_DIR` **at** `~/.claude` makes Claude Code read `~/.claude/.claude.json` instead of the real `~/.claude.json`, so that session runs with none of the user's project history and leaves a stub that then misdescribes the profile to this app. `~/.claude` is therefore selectable only by **removing** the variable, which is a third case the old boolean could not express — `ClaudeAccount.ActionFor` now returns `Inherit`/`Set`/`Unset` and `ApplyConfigDir` applies it (and flips `UseShellExecute` off only when it has something to do). The launch path, `QueryAuthStatusAsync` and `--profiles` all ask through it, keeping the property T136 established that they cannot drift; `--profiles` prints the three cases apart, because "nothing to do" and "remove the inherited one" look identical from the outside and mean opposite things. The Settings page's **Terminal default** row picks up the same rule: it was hidden for the *default* profile, and is now also hidden for `~/.claude` whichever profile happens to be default, since the `setx` form it prints is exactly the footgun there. Prerequisite for the rest of Block T: the moment the tray writes a user-wide variable itself, every profile launch is in the situation this fixes. Verified against a live machine-wide `CLAUDE_CONFIG_DIR`: `--profiles` reports `CLAUDE_CONFIG_DIR removed — inherited …\.claude-pessoal would select another profile` for the home profile and a plain set for the other, `ProcessStartInfo.Environment.Remove` confirmed to leave the child with the variable genuinely undefined, and a UI-Automation-driven screenshot with the profile combo on Trabalho confirming the terminal row is gone.

## Block S — Settings round-trip

- **T141** — A field missing from the Settings copy is a field **reset**, and the copy is now total by construction. `SettingsWindow` built its edit buffer with a hand-written field list (so Cancel leaves the caller's model alone) and `ApplySettings` copied the whole model back the same way — which means any field absent from that list started at its **default** and was written straight over the user's value on Save. Two instances, both found by accident rather than by looking: `MonitoredConfigDir` (fixed in T126 — every visit to Settings sent the tray icon back to the default profile) and `NotifyOnContextGrowth` + `ContextNudgeTokens`, still live until now: the context-growth toggle opened *off* no matter what was on disk, and saving the page turned it off. The window clones what it is given; `ApplySettings` takes the edited model whole (`_settings = updated.Clone()`) and keeps only the genuine side effects as explicit follow-up calls: clearing an in-progress flash frame, pinning the icon when the chosen profile changed, dropping the follow state, rebuilding the profile menu. Verified end to end rather than by reading the diff: seeded `settings.json` with distinctive values, then a UI-Automation check under `--settings-tray` read the toggle and slider back as **On / 33000** — and the same check against the pre-fix constructor reads **Off / 15000**, so it is a real pass and not a green that could never go red; then the full round trip through the **real tray** (right-click the notification icon, open Settings, click Salvar) left all 19 fields intact on disk, `Metric` and `MonitoredConfigDir` included. No user-visible strings and no new feature: the fix is that a setting you turned on stays on.
- **T229** — Save merges by which write is newer instead of by ownership: any field the page left at the value it opened with takes the live one, so a toggle flipped in the tray menu with Settings open is no longer written back over - and with it T171 machine-wide environment write, which reconciles off the value Save had been restoring.
